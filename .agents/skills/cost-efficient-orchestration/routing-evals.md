# Routing evaluation prompts

Use these cases after changing routing policy, descriptions, or host mappings. Evaluate a bounded representative set in an independent planning-only pass; prohibit edits, delegation, and external mutation. Where available, use fresh context per case; otherwise record that the cases shared one reviewer context. Give the evaluator prompts and raw policy/configuration, not expected answers. These are behavioral evaluation cases, not automated tests or evidence of runtime launches. Unless a case says otherwise, its hypothetical host advertises the four current unpinned profiles, supports explicit model/effort controls, and has no known quota block.

| --- | --- |

Do not choose writable Coder merely to obtain Spark. |

| Independently check a bounded engineering cleanup with objective tests and no consequential inference. | `routine-review`; when an independent Reviewer is warranted, use the maintained Codex Reviewer route with explicit Sol/high. For a trivial objective check, run the command directly instead of creating a cheaper pseudo-reviewer. |
| A one-line cohort exclusion change affects inferential conclusions. | Not a routine review merely because the diff is small. Classify S3 or higher as warranted, preserve independent consequential review and numerical/scientific evidence. |
| A Sol/high Chief receives one frozen module whose immutable behavioral tests fail; only its implementation file may change and the known test command must pass. | S1; named Coder / Spark / medium. ## Acceptance

Pass a policy review only when each route keeps task method, concrete task kind, execution contract, model/effort, and assurance distinct; preserves S0–S4 authority, privacy, the four-role ceiling, one-open-thread-per-role rule, one-active-writer rule, and no recursion; makes the combined decision before mutation/delegation; and distinguishes configuration, policy freshness, and runtime observations. Compare the task-kind matrix with actual absent model/effort TOML keys, explicit launch arguments, stale-host limitations, and effective permissions. Confirm a direct known command is not delegated, unused roles are not launched, eligible bulk work leaves an expensive Chief, Builder/Coder writes are serialized, Sol/high is the maintained Reviewer start, known quota blocks are filtered before launch, waits do not create replacements, closure is reported honestly, and verification stays meaningful and bounded. Usage evaluations must identify host/project scope, separate current, mixed, and stale/unknown cohorts, count only actual launches, and state token coverage. Record any disagreement as a role/model mismatch, task-kind mismatch, unjustified escalation, missed offload or balanced opportunity, metadata-provenance failure, policy-cohort error, unsupported host action, lifecycle error, or proof overclaim. Make the smallest evidence-backed wording change; do not tune from a single prompt.

Any case that mutates code, configuration, executable workflow, or routing behavior must be S1 or higher. A host metadata probe may resolve runtime fields and inform a new current-phase plan, but it cannot recover original launch intent or manufacture model-quality evidence.
