# Task record: research Skills V0.1

## Intent

- Objective: Turn the reviewed research-capability landscape into a minimal set of usable, portable Skills that Chief can select on demand.
- Non-goals: Install third-party agent systems, create a generic research-execution Agent, duplicate orchestration rules, prescribe one model per research task, or create placeholder Skills.
- Scope: Evidence review, hypothesis and study design, paper-code reproduction, scientific figures, and research software lifecycle.

## Chief decision

- Risk: S1. These are execution and evidence contracts; this task does not analyze project data or make a scientific claim.
- Execution: Direct, with no worker.
- Routing boundary: The specialized Skill owns method and deliverables; `cost-efficient-orchestration` owns model choice, delegation, and S0-S4 assurance; the working project owns local scientific and infrastructure facts.
- Verification: Validate each Skill, inspect discovery descriptions and reference routing, test installation of all Skills, check local links, and scan public text for private machine identifiers.
- Stop conditions: No tool credentials, external installations, generated scripts, empty scaffolds, or copied third-party manuals.

## Implemented Skills

| Skill | Modes or decisions | Main acceptance boundary |
| --- | --- | --- |
| `evidence-review` | rapid scan, bounded evidence map, systematic or novelty review | Conclusion cannot exceed the frozen search boundary |
| `hypothesis-study-design` | competing hypotheses, discrimination, study and statistical plan | Coherence is not evidence; human freezes confirmatory choices |
| `paper-code-reproduction` | understanding map, smoke reproduction, claim-level reproduction | Code runs, method implemented, and claim reproduced remain separate |
| `scientific-figure` | code-first results, editable architecture, method schematic, domain visualization | Visual appeal cannot replace provenance or scientific checks |
| `research-software-lifecycle` | one-off, internal reuse, public software, HPC or pipeline | Engineering effort grows only with the chosen maturity target |

Each Skill has one focused reference loaded only for advanced modes or domain checks. External repositories and standards remain cited sources or optional tools rather than bundled dependencies.

## Integration

- Chief matches the user request against the five Skill descriptions.
- Only the selected `SKILL.md` is loaded; its reference is opened only when the chosen mode needs it.
- The installer discovers every valid directory under `.agents/skills/` and links all Skills at user scope. Claude Code receives equivalent links under its native Skill directory.
- Project instructions can strengthen data, ethics, compute, and acceptance rules but do not copy or weaken the shared method contracts.

## Verification and decision

- Skill validation: All six repository Skills passed the Skill validator, including the shared orchestration Skill.
- Installer checks: Shell syntax passed. Isolated `portable`, `claude`, and `all` installs produced six portable links, six Claude links when selected, and four Codex role links; dry-run, update, status, user-owned configuration conflict, and unsupported-host guards passed.
- Link, privacy, and diff checks: Local Markdown links and whitespace checks passed. Public text contains no machine-local path or account identifiers, and specialized Skills contain no host model names.
- Outcome: Accepted as research Skills V0.1. The five research methods are discoverable, portable, installed together, and remain separated from model and assurance routing.
- Remaining uncertainty: Real routing quality, model sufficiency, and cost savings require calibrated tasks rather than document inspection alone.

## V0.1.1 model-routing refinement

- Decision: Keep one dispatcher. A matching research Skill now gives the starting capability for its known work units; the host adapter resolves that need to Luna, Terra, Sol, or an equivalent model. Work outside those rows falls back to the original limiting-factor policy.
- Separation: Task type selects the Skill, work-unit difficulty selects model capability, and S0–S4 selects assurance. Risk does not automatically upgrade the executor.
- Codex start: Terra / medium Chief, Luna / medium Scout or Coder, Terra / medium Builder, and Sol / high Reviewer; switch Chief to Sol only when the main judgment itself needs it.
- Cost intent: Keep corpus-scale retrieval and frozen edits on fast workers, reserve balanced models for synthesis or coordinated builds, and reserve strong models for ambiguous judgment or independent review.
- Limitation: Markdown can guide routing and configured subagents, but it cannot switch the active Chief model. Actual savings still need measurement on repeated task classes.
- Verification: All six Skill validators, the installer shell check and portable dry-run, whitespace check, and private-path scan passed.

## V0.1.2 concept and adoption clarification

- Decision: Replace the ambiguous conceptual use of *role* with **execution contract**. Scout, Coder, Builder, and Reviewer now mean scope, permissions, ownership, and independence; they do not mean low, medium, or high intelligence.
- Four decisions: Task method selects the process; execution contract selects the work boundary; model family and reasoning effort select capability; S0–S4 selects evidence, independent review, and human acceptance.
- Routing map: README now places general work and all five research Skills against Chief and the four execution contracts. This is a lookup table, not a standing team; direct work or one bounded worker remains the default.
- Current adapter: The existing Codex profiles remain Luna / medium for Scout and Coder, Terra / medium for Builder, and Sol / high for Reviewer. They are simple host defaults, not conceptual identities. Dynamic decoupling is deferred until repeated behavior and cost tests justify it.
- Upstream control: Every Skill now states its selected and non-selected ideas. The ecosystem adoption ledger records upstream examples, selected contracts, deferred adapters, deliberate exclusions, and known gaps.
- Scope boundary: No new Skill, external tool, runtime, model binding, or untracked asset was added. Scientific data analysis, claim-linked writing, executable adapters, and cost-quality benchmarking remain explicit candidates rather than placeholder folders.
- Verification: All six Skill validators passed; installer shell syntax and the portable dry-run passed; local Markdown links and whitespace passed. The changed public text was scanned for machine-local paths and stale three-part routing language.
- Remaining uncertainty: The conceptual separation is now explicit, but actual token, latency, quality, and routing gains still require a small repeated-task benchmark and receipts from real projects.
